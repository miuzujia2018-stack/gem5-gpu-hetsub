# 固定系统实验平台下，尽可能忠实复现 HetSub

日期：2026-10-15。状态：按本方案实施中；合成机制证据与未完成项见[执行报告](../.ai/reports/REPORT.md)，应用和最终验收尚未完成。

## 1. 推荐结论

固定 gem5-gpu、VI_hammer、CPU/GPU/缓存/目录配置、64个tile位置、应用与输入、系统时钟和Docker环境；把 **NoC内部架构作为被比较的方法**，允许在相同tile之间重新组织子网、带宽和缓冲资源。

在这一边界内，可以实现论文的主要架构机制：独立dual-line与Mesh子网、真实宽窄flit、独立仲裁与背压、PG、静态long-link、relay及两个算法。不需要迁移Noxim或运行SNN系统，但需要对flexible Garnet进行有边界的网络模型改造，工程量属于中等，不能描述成只改一个路由函数。

如果“平台不变”还要求每条链路宽度、每个router的所有端口、VC和仲裁器完全不变，则无法忠实复现HetSub。此时只能采用上一版的共享Mesh适配，并以HetSub-inspired命名。

本文件替代 [最小适配方案](HETSUB_MINIMAL_BASELINE_PLAN.md) 的主架构建议。上一版保留为严格限制NoC硬件变化时的退路；其代码审查、时间单位问题、构建门禁、正确交付检查继续有效。此前对“七成/四五成相似度”的口头估计不是验证指标；后续以逐项机制和测试证据判断忠实程度。

## 2. 哪些固定，哪些允许改变

| 层次 | 处理 |
|---|---|
| 仿真器、CPU/GPU执行模型、Ruby协议 | 固定 |
| 应用二进制、数据、运行条件 | 固定，与bak/TBP逐项对齐 |
| CPU/GPU/目录到tile的映射 | 固定，使用相同实际映射列表 |
| tile数、8×8坐标和相邻tile之间的物理走线位置 | 固定 |
| 子网数量、同一相邻连接上的数据通道宽度分配 | 允许改变，属于HetSub本身 |
| VC数量、位宽、端口数量、仲裁域和电源域 | 按论文建模，用总资源比较，不能仅比较VC个数 |
| 统计定义、测量窗口、功耗参数来源 | 三种方法统一 |

主比较应称为“同系统平台上的NoC方案比较”。只有XY、bak、TBP共享相同网络资源时，它们之间的差值才可主要归因于路由；HetSub还包含架构变化，结果解释需要保留这一点。

## 3. 必须优先保留的架构

### 3.1 一个Ruby network，两个独立子网

保留一个GarnetNetwork和既有64个tile/router坐标。建议每个Router对象内部维护两个小的子路由器状态集合，并复用已有分配/转发代码：

| 属性 | L：常开dual-line | M：可PG Mesh |
|---|---|---|
| 方向 | Hilbert前驱、后继及本地端口 | 东西南北及本地端口 |
| 每协议vnet的VC数 | 1 | 2 |
| 每VC深度 | 4个本子网flit | 4个本子网flit |
| 仲裁、流控、VC状态 | 独立 | 独立 |
| 路由 | Hilbert序号单调 | 严格XY |
| PG | 常开 | ACTIVE/SLEEP/WAKING |

独立指实际能够在各自配置容量内并行传输，不是给同一个出端口队列加两种标签。两子网各有NetworkLink实例，链接同一组tile坐标；Hilbert只连接相邻tile，没有新增跨芯片远距离连线。

Router对象数量不是硬件资源指标。64个软件对象各含两个子路由器，仍应在报告中记为64对逻辑子路由器。不要为了维持“64 routers”字样而隐藏第二套控制资源。

原始代码很多位置使用全局`m_num_vcs`、单个direction→port、单个NI输入/输出link，必须改为子网感知；可以增加一个简单state struct或subnet索引，不建立通用插件框架。共享代码可以，共享本应独立的仲裁状态不可以。

### 3.2 真实flit宽度和容量

以当前单网128-bit基础宽度W为尺度，论文比例配置为L=128 bit、M=64 bit。源NI先确定子网，再按真实消息字节数产生`ceil(message_bytes / subnet_flit_bytes)`个flit。控制包和数据包长度来自Ruby协议，不固定成论文的2/4个flit。

每个子网每条链路每周期最多发送其自身宽度对应的一个flit。窄flit数量更多，必须真实占用更多队列槽、链路服务与VC持有时间，不能只在最终统计上补延迟。buffer资源按bit计算；保持原协议vnet隔离，不能将不同消息类别合并以节省空间。

NI仍连接原来的Ruby MessageBuffer。原有tile外部注入/弹出总带宽保持基线预算，使用入口MUX/调度约束；不能因拥有两条子网接入链路就把tile注入能力无意翻倍。同一消息只注入一次，多播按原框架拆成单播后各自准确计数。

## 4. 公平资源预算必须算到整个有限Mesh

论文正文以内部router的端口数解释带宽相等：`2W + 4(W/2) = 4W`。这个等式不自动保证8×8边界网络的总链路位宽相等。

对当前开放边界8×8：Mesh有112条无向边，Hilbert线有63条无向边。以下预算仅计算内部有向链路，全部按一个相邻tile间距计：

```text
基线：       224 × 128 = 28672 bit/cycle
论文比例：   126 × 128 + 224 × 64 = 30464 bit/cycle
比基线多：   6.25%
```

这是本网络尺寸下的建模资源核算，不是对原论文总体公平性的判决。外部NI、控制存储、relay等还要另计。

建议保留两套明确配置，避免把“更忠实”和“完全等预算”混为一谈：

| 配置 | L/M宽度 | 作用 |
|---|---|---|
| `paper-ratio` | 128/64 bit | 保留论文2:1比例，验证主要性能机制；如与bak/TBP比较，必须披露内部链路预算多6.25% |
| `matched-budget` | 128/56 bit | `126×128 + 224×56 = 28672`，严格匹配当前Mesh内部总链路位宽；作为等预算比较的主配置 |

56-bit是资源归一化变体，不是论文原参数。转换器按字节流支持一般宽度，不能硬编码“一宽flit正好拆两个窄flit”。两配置都沿用相同时钟、应用和映射。不能把两配置中较好的结果按工作负载拼接。

实际实施另发现：NI处L/M独立接入线路的安装位宽在128/64与128/56下分别高于单网50%与43.75%，尽管共享服务机会限制了NI吞吐；内部链路等预算不代表外部线路或总面积相等。数据存储、传播模型与PG能量边界见[资源审查](../.ai/reports/RESOURCE_AUDIT.md)。

总buffer bits用实际分配的port、vnet、VC、深度、位宽相乘求和，必须包括NI与relay；软件固定大小容器不能充当免费模型缓冲。L每vnet 1个宽VC、M每vnet 2个半宽VC，不能按“1+2比基线2多”简单认定buffer增加。相反，是否降低资源还取决于端口数和relay开销。

每个子网都保留独立容量，严格等预算配置也只改变宽度，不退回共享单端口。无法支持56-bit时，应先明确报告128/64版的预算差异，不能声称已做完全等带宽比较。

## 5. 原文控制与长链路

### 5.1 动态分流与PG

实现原文III-A-2：低负载全部优先L；L接近拥塞才按local/global分离；M拥塞时降低global转入比例；占用信号使用滞回。参数和反馈范围原文没有充分规定的部分，要列为实现选择，不能宣称逐位一致。

CPU/GPU消息的local/global可采用Hilbert距离阈值，但须标为迁移定义。运行前测量实际locality，不改变节点映射或输入来保证收益。 ordered vnet若不能证明跨子网仍保序，则固定在M/XY，并报告其占比；这是协议适配偏差，不用复杂reorder buffer掩盖。

ordered vnet还需沿用单一可用VC或已有等价保序机制，不能仅固定XY就默认跨两个VC仍有序。当前一个tile可能连接多个协议控制器，实际local端口数必须保留并计入资源，不能套用原文“一tile一个local端口”的面积数值。

M中的buffer/控制独立进入PG；L不受影响，bypass使用的crossbar与必要控制保持供电。保留6-cycle唤醒和每次唤醒的转换能量；有在途flit、占用buffer、未完成请求时不能断电。状态周期、唤醒次数和实际服务延迟均需测试。

### 5.2 长链路采用论文已有的静态模式

两个单独模式：普通双子网动态选择；以及冻结shortcut配置、屏蔽普通M注入的long-link模式。测试开始前配置完成，运行中不改变。ordered流量在long-link模式固定确定性的L路径，拥塞时等待，不临时改道。

沿已有M物理链路构建最多2-hop的旁路路径。中间router不写buffer、不执行正常RC/VA；连接与crossbar仍消耗资源。NI端点执行真实序列化、反序列化和有界relay背压；只允许在目标有空间且静态路径可服务时发射。

为减少代码，允许一个短的composite-link适配器代理这段冻结路径，但必须引用原M链路清单、独占其已分配通路，禁止原M传输同时使用这些资源；统计仍归入真实物理段，不能添加无限容量的“远端直达边”。不需要全网预约调度器、运行时拓扑重配置或packet registry。

在128/64配置中，16-byte数据可形成两个8-byte传输；在128/56配置中按连续字节流分段重组，保存实际有效字节与head/tail语义。相邻宽flit边界不必与窄flit边界重合，不能对每个宽flit单独补齐导致虚增字节。最终Ruby消息在完整到达后交付一次。

论文的logical hop=1不能自动等同于当前2GHz硬件已实现一个cycle。提供原文抽象时序与较保守物理传播时序两种敏感性配置，写明建模假设；没有布线/时序验证时不宣称2GHz真实硬件闭合。不能通过统一增加原版HetSub的多跳路由延迟来冒充论文旁路。

### 5.3 两个算法都保留

Algorithm 1采用Hilbert区间的严格单调条件，shortcut终点不得越过最终目的或反向。正常与捷径路径均需保持依赖关系可解释。

Algorithm 2保留Hilbert分层U形子区、非相邻子区候选、高层优先、中心连接位置、真实流量阈值及crossbar冲突检查。最初允许固定两条shortcut用于功能验证；最终完成一个离线脚本，不实现在线优化器。同层排序、阈值及profile来源公开。

profile只来自独立pilot或预先指定的训练阶段，不能读取最终测试未来流量。跨仓库结果单列profile成本。固定几何配置是测试对照，不能替代Algorithm 2后仍宣称插入算法已复现。

## 6. 最小实施顺序

1. **统一平台与测量。** 处理旧方案已发现的配置、placement、NI交付、tick/cycle、packet统计问题，取得同配置XY基线。
2. **真实双子网与宽度。** 先不做PG和long-link；验证独立并行、buffer位数、真实flit数、流控与完整交付。
3. **选择策略与PG。** 加入滞回、唤醒和能量记账，形成普通HetSub架构模型。
4. **固定静态long-link与relay。** 单条、双条、冲突、目标背压测试；验证中间无buffer访问。
5. **离线分层插入。** 对固定方案比较，完成算法贡献。
6. **资源匹配与应用比较。** 两种宽度配置和两种运行模式分别报告，不事后挑选。

主要修改仍集中在Router、GarnetNetwork、NetworkInterface、NetworkLink与少量flit/VC元数据。拓扑构造增加子网数据链路并保留原tile映射；配置提供模式和宽度。源代码变化是中等规模的局部改造，不能再承诺上版“只重新分配两个现有VC”的改动量。

不重写Ruby协议、GPU模型，不升级gem5，不复制第二套系统；不同时开展Noxim复现、RTL综合和后端验证。若单Router内双状态复用反而产生大量分支，可改为复用同一router类实例化两组内部子路由器，但64个tile与端点映射必须固定；先选一种实现，不维护两套后端。

## 7. 对应的测试与验收

| 层级 | 必须观察到的证据 |
|---|---|
| 宽度/守恒 | 同一消息分别产生正确数量的128/64/56-bit flit；尾部有效字节正确；relay往返无丢失、重复和错误重组 |
| 独立性 | 两子网可按各自容量同周期前进；堵塞M不凭共享仲裁器阻止L；堵塞L不阻止M |
| 资源 | 所有内部/外部链路、buffer bits、NI/relay空间列账；matched-budget算式与实际配置一致 |
| 拓扑/路径 | 64×64路径、实际MachineID、多NI本地端口、vnet隔离、ordered顺序正确 |
| 无死锁范围 | 两子网及shortcut通道依赖检查；有限包、长包、多vnet、热点压力后全部排空；不把“未超时”当形式化证明 |
| 选择/PG | 给定拥塞信号触发正确比例与滞回；无在途资源断电；唤醒真实阻塞服务6周期；转换能量不遗漏 |
| bypass | 中间普通buffer/RC/VA活动为0；所引用M链路有真实传输；接收满时端点停发并可恢复 |
| 插入算法 | 分层规则、≤2-hop、端点度数与crossbar冲突检查；独立pilot来源有记录 |
| 应用 | backprop/kmeans原输入输出正确、正常退出；bak/TBP实际方法及阶段覆盖可观察 |
| 性能分析 | 原比例与等预算、普通与long-link分开报告；不要求HetSub胜出，也不沿用论文改善百分比 |

合成实验先保留旧三模式与一个小locality测试，再开展已有两应用。时间换算、排空、窗口、有限多seed、Docker干净构建和输出记录沿用旧方案第7–8节。数据路径改变后重新验证旧检查，而不是引用上一阶段通过记录。

统计必须以正确交付的message/packet、有效消息bytes和统一Ruby cycles为主。宽窄flit个数不同，不能用flits/cycle直接判定谁吞吐更高，也不能把flit平均延迟替代packet完成延迟。每子网flit/beat计数仅作机制分析；物理链路数量改变后，Jain等指标必须重新定义相同的比较集合，不能继续硬编码368。旧方案关于固定基础flit、共享物理端口、每vnet总共两个VC的假设已由本文件替换，不再作为验收要求。

两类结论分开：合成测试验证HetSub机制在本模拟器中的行为；CPU/GPU应用验证其迁移到当前平台的效果。后者不能复现原论文四个SNN应用的38%/58%等数值，也不能单凭它否定原文。

只使用AGENTS.md要求的现有源码/二进制构建凭据，无CSV哈希、逐包哈希、新数据库或额外审批体系。本轮为文档修订，没有构建或新仿真结果。

## 8. 可以使用的名称和结论

全部核心机制实现并通过测试后，可写：

> 在固定的gem5-gpu CPU–GPU系统平台上实现HetSub架构的周期级移植模型，保留异构独立子网、真实flit宽度转换、动态选择、PG和静态可重构长链路；分别报告论文比例与匹配内部链路预算的配置，并披露协议适配、时序与能量模型假设。
